# ADR-0001：BM25 索引的本地快照持久化

- **状态**：当前采用（Local MVP）
- **日期**：2026-07-29
- **决策范围**：`BM25Indexer` 的存储位置、文件格式、一致性边界和升级路径

## 背景

当前项目以本地优先、单进程运行和最小外部依赖为主要约束。C11 `BM25Indexer`
需要保存 Chunk 文档表、TF/DF/IDF、倒排 postings 和平均文档长度，使程序重启后
无需重新解析全部文档即可执行稀疏检索。

BM25 索引是由源文档和 SparseEncoder 输出生成的派生数据，可以通过重新摄取或
全量 rebuild 恢复，不是唯一事实来源。

## 决策

当前使用单个本地 pickle 快照：

```text
data/db/bm25/index.pkl
```

具体约定如下：

1. 默认目录为 `data/db/bm25/`，构造 `BM25Indexer` 时可以覆盖路径。
2. 真实索引位于被 Git 忽略的 `data/` 目录，不提交到版本库。
3. 每次更新后重新计算全局 IDF，生成完整候选快照。
4. 先写入同目录的 `index.pkl.tmp`，写完并刷盘后原子替换 `index.pkl`。
5. 快照带有版本号；加载时校验文档数、统计数据和倒排索引的一致性。
6. 当前运行假设是**本地可信文件、单写者、语料可整体装入内存**。
7. C14 组装 Pipeline 时，应把默认路径接入正式配置，而不是由上层依赖默认值。

## 为什么当前合理

| 关注点 | 当前收益 |
|--------|---------|
| 部署 | 只使用 Python 标准库，不新增数据库或搜索服务 |
| 恢复 | 进程重启后直接加载快照；损坏时可从源文档重建 |
| 一致性 | IDF 每次按完整语料重算，避免增量统计漂移 |
| 写入安全 | 临时文件加原子替换，写入失败不会留下半个正式快照 |
| 仓库卫生 | 派生索引放在 `data/` 并由 `.gitignore` 排除 |
| 演进成本 | 上层依赖 `BM25IndexStore`，以后更换实现无需改变调用契约 |

这个选择适合当前的个人、本地、小规模知识库，但不是通用的生产级结论。

## 已知顾虑与残余风险

| 风险 | 可能后果 | 当前控制 | 尚未解决的边界 |
|------|---------|---------|----------------|
| pickle 加载不可信文件 | 被篡改的 pickle 可能在反序列化时执行代码 | 只从项目本地数据目录加载；不接收上传或网络下载的索引 | 若索引需要共享或来自外部，必须更换安全格式 |
| 多进程并发写入 | 两个写者都从旧快照计算，后写者可能覆盖先写者的更新 | 单写者运行假设；原子替换只防文件写坏 | 当前没有文件锁、事务或冲突检测 |
| 更新采用 O(N) 重建 | 语料增大后，单次 upsert 延迟和磁盘写入量持续上升 | 实现简单且保证全局 IDF 正确 | 当前没有增量 DF 表、分片或局部 postings 更新 |
| 整库驻留内存 | 大语料可能造成启动慢或内存压力 | 当前目标语料规模较小 | 当前没有按需加载、mmap 或分页查询 |
| Chroma 与 BM25 分开写入 | 某一路成功、另一路失败时可能暂时不一致 | BM25 是派生数据，可通过 rebuild 恢复 | C14 仍需定义失败恢复、重试或重新摄取策略 |
| 路径尚未接入 `settings.yaml` | 不同入口可能意外使用不同目录 | 构造参数允许显式覆盖 | C14 装配时必须统一配置来源 |
| 快照格式与 Python 实现耦合 | 跨语言读取困难，长期兼容性较弱 | 快照带版本号，损坏或不兼容时明确失败 | 没有跨版本迁移工具，当前采用重新构建 |

原子替换只保证“文件不会只写一半”，不保证多个写者之间的逻辑事务，也不保证
Chroma、BM25、ImageStorage 和文件完整性记录之间形成跨存储原子提交。

## 恢复策略

- 正常启动：读取并校验 `index.pkl`。
- 写入中断：正式快照保持不变；遗留临时文件不作为索引加载。
- 快照损坏或版本不支持：加载失败并报告具体索引路径，不静默使用部分数据。
- 需要恢复：删除损坏快照，从受信任的源文档重新摄取并全量 rebuild。
- 跨存储部分失败：在 C14 主流程中按源文档重新执行相关存储步骤；在该策略落地前，
  不声称多存储具有事务一致性。

## 备选方案

### JSON 快照

优点是可读、跨语言且不会像 pickle 一样在加载时执行代码；缺点是文件通常更大、
浮点和嵌套结构校验仍需自行维护，仍然没有并发写事务。适合需要交换索引但规模仍小
的场景。

### SQLite

可以提供事务、并发控制和增量更新，适合多个摄取任务或更大本地语料。代价是需要
设计 documents、terms、postings 和统计表，并正确维护 DF/IDF 更新。它是当前方案
最直接的下一步升级路径。

### Tantivy、Elasticsearch 或 OpenSearch

适合大规模、共享或分布式检索，提供成熟的索引、并发和查询能力；代价是额外依赖、
部署和运维复杂度。当前阶段没有证据表明需要承担这些成本。

## 升级触发条件

出现下列任一情况时，应重新评估当前决策：

- 需要两个或更多进程/机器同时摄取；
- 实测全量重建时间已经影响正常开发或摄取流程；
- 索引内存占用接近运行环境预算；
- 索引需要在用户、机器或服务之间传输；
- 索引文件可能来自不可信来源；
- 需要 Chroma 与稀疏索引之间更强的事务或恢复保证；
- 需要跨语言读取、在线迁移或长期格式兼容。

推荐演进顺序：

```text
本地单写者、小语料
index.pkl + 原子替换
          │
          ▼
本地并发或中等语料
SQLite 文档表 + postings + 事务
          │
          ▼
共享、大规模或分布式检索
Tantivy / Elasticsearch / OpenSearch
```

升级应由测得的并发、延迟、内存或共享需求触发，不按假设提前引入复杂后端。
