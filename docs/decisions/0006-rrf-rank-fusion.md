# ADR-0006：用 RRF 合并 Dense 与 BM25 排名

- **状态**：当前采用
- **日期**：2026-07-30
- **决策范围**：D2 DenseRetriever 与 D3 SparseRetriever 的候选结果如何形成统一排名
- **说明**：本文记录当前实现知识、示例和顾虑，不修改 `DEV_SPEC.md`

## 先用一句话理解

RRF 不负责重新检索，也不调用模型。它只做一件事：

> 接收 Dense 和 BM25 各自排好的榜单，根据候选项在两张榜单中的名次，重新生成一张总榜。

```text
D2 Dense 排名  ──┐
                 ├─> D4 RRFFusion ─> 统一候选排名
D3 BM25 排名   ──┘
```

## 为什么不能直接相加原始分数

两条召回通道的分数含义不同：

```text
Chroma distance = 0.08  越小越相似
BM25 score      = 12.5  越大越相关
```

`0.08 + 12.5` 没有可解释的统计含义。对两路分数先做归一化也需要额外假设，并且不同
语料、查询和后端下的分布会变化。RRF 因此放弃比较原始分数，只使用每一路已经给出的
相对名次。

## 当前公式

一个候选项在一条榜单中的贡献为：

```text
contribution = 1 / (k + rank)
```

它出现在多条榜单时，把各路贡献相加：

```text
rrf_score(chunk) = sum(1 / (k + rank_in_each_list))
```

当前默认 `k = 60`。`k` 越小，榜首与后续名次的相对差距越明显；`k` 越大，名次贡献
越平滑。它不是模型参数，也不改变 Dense 或 BM25 自己的搜索结果。

## 完整例子

知识库中有四个 Chunk：

```text
A：发布时必须同时校验 generation 和 claim_token。
B：租约过期后，新 worker 会接管任务，旧 worker 会被 fenced。
C：SQLite WAL 可以防止数据库记录写坏。
D：处理时间较长时，可以调用 renew_lease 续租。
```

用户查询：

```text
租约过期后，旧 worker 为什么不能发布结果？
```

两路召回分别给出：

```text
Dense 排名                 BM25 排名
1. A                       1. B
2. B                       2. D
3. C                       3. A
```

默认 `k=60` 时：

```text
第 1 名贡献 = 1 / 61 = 0.01639
第 2 名贡献 = 1 / 62 = 0.01613
第 3 名贡献 = 1 / 63 = 0.01587
```

合并结果：

| Chunk | Dense 贡献 | BM25 贡献 | RRF 总分 |
|-------|-----------:|----------:|---------:|
| A | 0.01639 | 0.01587 | 0.03226 |
| B | 0.01613 | 0.01639 | 0.03252 |
| C | 0.01587 | 0 | 0.01587 |
| D | 0 | 0.01613 | 0.01613 |

最终总榜：

```text
1. B  0.03252
2. A  0.03226
3. D  0.01613
4. C  0.01587
```

B 不是因为某个原始分数更大，而是因为 Dense 把它排第 2、BM25 把它排第 1，两条
独立召回路线都认为它靠前。

## 当前实现约定

1. `rank` 使用候选项在输入榜单中的实际位置，从 1 开始计算；不信任对象中可能残留的
   旧 `candidate.rank`。
2. 同一个 Chunk 在不同通道中出现时累加贡献。
3. 同一个 Chunk 在同一通道中意外重复时只贡献一次，避免单路重复加权。
4. 输出重新编号为连续的 `rank=1..top_k`，并把 `source` 改为 `fusion`。
5. 输出 `score` 是 RRF 总分，不再是 Chroma distance 或 BM25 score。
6. 原始通道、排名和分数保存在 `debug.rrf.sources`，只用于解释和调试。
7. RRF 分数完全相同时，按首次出现的通道、通道内位置和 Chunk ID 稳定排序。

示意输出：

```python
RetrievalCandidate(
    chunk_id="B",
    score=0.03252,
    source="fusion",
    rank=1,
    debug={
        "rrf": {
            "k": 60,
            "score": 0.03252,
            "sources": [
                {"source": "dense", "rank": 2, "score": 0.20},
                {"source": "sparse", "rank": 1, "score": 12.5},
            ],
        }
    },
)
```

## 为什么当前合理

| 关注点 | 当前收益 |
|--------|---------|
| 分数量纲 | 不需要假设 distance 与 BM25 score 可以直接比较 |
| 后端替换 | 更换 Embedding、向量库或 BM25 实现后，融合公式仍可使用 |
| 稳定性 | 同样的输入榜单总是产生同样的结果 |
| 可解释性 | 可以明确展示每条通道贡献了哪个名次 |
| 成本 | 纯内存排序，不调用额外模型或远程服务 |
| 复杂度 | 公式和状态都很小，适合作为混合检索基线 |

## 已知顾虑

### 1. RRF 丢弃原始分数强弱

同一条通道中，第一名可能远好于第二名，也可能只略好一点。RRF 只知道名次，不知道这个
差距。因此它稳定、通用，但不一定是理论上的最佳融合方法。

### 2. 两路当前权重相同

Dense 和 BM25 的相同名次贡献完全一致。当前没有 weighted RRF，也没有按查询类型动态
调整通道权重。是否需要权重必须由召回评估证明，不能只凭直觉添加。

### 3. 候选集截断会影响融合

如果某个正确 Chunk 在 Dense 中排第 21，但 Dense 只取前 20，它在 RRF 中就像“没有被
Dense 命中”。因此 Dense/Sparse 的召回深度会直接影响融合结果。

### 4. 完全同分时存在输入顺序偏好

如果 D5 固定先传 Dense 榜单，完全同分且首次位置相同等级时，Dense 侧先出现的候选会
优先。这只是保证确定性的 tie-break，不是额外的业务权重，但评估时仍需知晓。

### 5. `k=60` 是基线，不是已经验证的最优值

默认值来自常见 RRF 实践。当前项目还没有通过黄金查询集证明 60 优于其他取值。不要把
默认值误解为针对当前语料调优后的结论。

## 如何量化是否有效

应在 D5 完整混合检索可运行后，对同一批黄金查询比较：

```text
Dense only
BM25 only
Dense + BM25 + RRF
```

主要指标：

- Hit Rate@K：正确来源是否进入前 K；
- MRR：第一个正确结果通常排多靠前；
- NDCG@K：多个相关结果的整体排序质量；
- 单路独有命中与双路重叠命中的比例；
- 不同 `k` 和不同召回深度下的消融结果。

只有 RRF 在固定测试集上稳定优于单路结果，才能说明它对当前项目有效。当前 D4 的单元
测试证明的是公式、确定性和边界行为正确，不证明业务召回质量已经达标。

## 升级触发条件

出现下列情况时重新评估当前方案：

- 混合检索的 Hit Rate、MRR 或 NDCG 长期不如某个单路；
- 某一通道质量明显更高，需要有证据的权重调整；
- 候选截断导致大量正确结果无法参与融合；
- 需要利用校准后的原始相关性分数，而不仅是排名；
- 查询类型差异明显，需要按关键词型、语义型查询动态选择策略。

可选演进包括 weighted RRF、分数校准后的加权融合、学习排序或查询路由。它们都比当前
方案复杂，应由评估数据触发。
